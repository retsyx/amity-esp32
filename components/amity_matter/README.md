This component exposes endpoint 1 as a Basic Video Player and endpoint 2 as a
Speaker, using the installed ESP Matter data model and CHIP cluster delegates.
Endpoint 3 is a Power Source named "Remote battery", with Battery and Rechargeable
features. `BatPercentRemaining` uses Matter half-percent units (100% = 200);
`BatChargeState` reports charging, not charging, or unknown. No paired remote
reports 100%/not charging. A paired but disconnected remote reports null percentage
and unknown charging. Missing readings while connected also remain unknown.
The endpoint does not claim to power the player, speaker, or ESP32. An independent
application task publishes BLE readings once per second with
`amity_matter_update_remote()`, outside the BLE host task and its locks.

Initialize NVS, supply activities and initial hub state, then call
`amity_matter_start()`. Matter initializes WiFi and NimBLE. Start the keyboard
client after it; keep `CONFIG_USE_BLE_ONLY_FOR_COMMISSIONING=n` so commissioning
does not reclaim the shared BLE host.

Endpoint 0 exposes Diagnostic Logs, General Diagnostics, and Wi-Fi Network
Diagnostics. Diagnostic Logs serves the existing bounded runtime log ring for
EndUserSupport and NetworkDiag intents. ResponsePayload returns the newest bytes
that fit the response; BDX downloads an independent snapshot of the whole retained
ring. Snapshots are released on completion or cancellation. CrashLogs returns
NoLogs because this firmware does not retain crash dumps across resets. Timestamps
are omitted rather than assigning a capture time to older retained entries.

General Diagnostics includes NetworkInterfaces, RebootCount, UpTime,
TotalOperationalHours, BootReason, and the standard fault/boot events. The SDK
provides reset reasons and interface information. Operational time accumulates
from the first boot of firmware with diagnostics enabled, persists in NVS hourly,
and checkpoints on an orderly reboot. Unexpected power loss or a crash can lose
the time since the last checkpoint (at most one hour). Factory reset clears it.
Fault events use the SDK notification hooks; no additional fault sensors are added.

Wi-Fi Diagnostics exposes BSSID, security type, Wi-Fi version, channel, RSSI, and
the SDK's disconnection, association-failure and connection-status events. Packet
and error count features remain disabled: the installed ESP32 SDK has no supported
API for those counters. No SDK source or packet paths are modified.

The application callbacks enqueue hub work and return whether the queue accepted
it. They must never wait for CEC, and must not call Matter while holding a lock
also used by a callback. Publish changes with `amity_matter_update_state()` from
the hub worker after releasing its locks.

Media Input entries are configured Amity activities. Playback supports Play,
Pause, Stop, Previous and Next; its required CurrentState attribute describes the
last accepted transport command. CEC cannot verify the media source's actual
playback state. Optional timeline, position, seek and track features are absent.
Keypad Input supports navigation, location and number keys using their native CEC
key codes. Showing or hiding an on-screen input list is not supported.

Speaker On means unmuted and Off means muted. The application must implement
discrete mute/unmute or return an error; toggling blindly cannot satisfy these
commands. The non-nullable OnOff attribute returns a read error until the hub has
observed audio mute status. CurrentLevel is null until observed, and uses Matter's
0–254 range when known. Ordinary Level Control Step emits the requested number of
relative volume keypresses. Absolute levels, continuous movement and the commands
which couple levels to OnOff return UnsupportedCommand. The component does not
fabricate an absolute level by counting keypresses.

Commissioning PIN, discriminator and salt come from the validated `amity_factory`
record generated by [amity-provision](../../amity-provision/README.md). The custom
CommissionableDataProvider derives the SPAKE2+ verifier from these values.
Only the current version-3 factory record is supported. Missing, erased, corrupt
or older provisioning data fails initialization without generating a new code.
The factory record also supplies the network hostname. The station interface receives it before
Matter starts Wi-Fi, so DHCP uses the provisioned name from the first request.
The composition layer uses the same name for the HTTPS mDNS alias. Enable `CONFIG_CUSTOM_COMMISSIONABLE_DATA_PROVIDER=y`.
Keep the onboarding code within the authenticated admin interface or local setup
console. The SDK's development attestation credentials are suitable for testing;
a commercially certified product needs provisioned production attestation data.

Fabrics are retained by Matter's NVS storage across OTA updates. The admin UI
always hides Apple's Keychain fabric (commissioner vendor 0x1384), including when
it is the only remaining fabric; it does not count as a visible connection.
When the last committed Apple Home fabric (0x1349) is removed, whether by Apple
Home or the admin API, a FabricTable delegate schedules removal of the remaining
Keychain fabrics after the original removal callbacks finish. Other platforms
and Keychain credentials supporting another Apple Home are retained. A pending
cleanup marker is persisted before the last Home is deleted and resumed after
reboot. In-flight commissioning is allowed to finish or roll back first; rolling
back an uncommitted Home never triggers cleanup. Keychain-only fabrics created
without a Home removal are hidden and retained, since iOS also uses them to
commission other ecosystems. Fabric records have no persistent parent link:
this last-Home policy uses Apple's known vendor IDs, rather than fabric IDs,
labels or commissioning order as a guessed one-to-one association.

Removing fabrics does not factory-reset the device or erase WiFi, BLE bonds or
Amity configuration. Commissioning windows are explicitly opened for 180–900
seconds. The component does not open a new window automatically when a fabric is
removed.

`tests/matter_commission.py` provisions a device using a private WiFi JSON file
and the local onboarding payload. `tests/matter_hardware.py` verifies endpoint
types, cluster lists, observable attributes and unsupported-command responses
with a real `chip-tool` controller. Keep its controller storage directory between
runs to verify reboot and OTA persistence. `--exercise-controls` additionally
sends commands to the currently configured activity and should be paired with a
CEC bus capture when checking the physical output.

`tests/matter_pi_controller.py` provides the same checks through the official
CHIP Python API when the host's Bluetooth controller is unreliable. Its optional
commissioning credentials file must have mode 600; omit `--credentials` on later
runs to reuse the established fabric. Run it in the documented private mount
namespace with dependencies and storage beneath the harness's `esp32` directory.
`--pase-only` checks the clusters over BLE before WiFi provisioning; it does not
establish a persistent fabric or verify operational WiFi connectivity.
Keep all native controller output private because SDK diagnostics can contain
onboarding and network credentials.
The pinned dependency setup and private invocation are documented in
[`tests/matter_pi.md`](../../tests/matter_pi.md).
