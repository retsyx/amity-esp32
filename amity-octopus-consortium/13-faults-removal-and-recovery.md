# 13. Faults, removal, and recovery

**20 October 2026 controller-policy amendment:** [Original controller and subordinate devices](21-original-controller-policy.md) is normative. The original first-setup Amity alone hosts the UI/integrations and sole remote; added devices are UI-less actuators, never input gateways or successor controllers.

## Purpose and governing rules

This is the proposed v0.1 lifecycle contract for OCTOPUSES in a CONSORTIUM. It distinguishes loss of connectivity, intentional retirement, actuator replacement, the prohibition on controller transfer, and original-controller recovery. None of these distributed lifecycle features is implemented by the baseline Amity commit `d50af8026938797fc0820d0107f4c4e064c2d2bc`.

The coordinator is fixed in v1. A timeout does not elect another coordinator, authorize a member to self-promote, or turn an inline member into an independent activity controller. Configuration replicas help reconstruct the system; they are not credentials to take it over. [09](09-membership-security-and-enrollment.md) defines the membership trust relationship, and [08](08-consortium-transport-and-routing.md) defines freshness, acknowledgment, and execution leases.

Local CEC isolation is independent of every network lifecycle. An offline, retired, or recovering OCTOPUS must continue preventing an isolated source's unauthorized activation/routing traffic from crossing its tentacle. A software failure must not connect the two CEC wires electrically. Hardware and semantic policy requirements are in [04](04-hardware-and-cec-runtime.md) and [06](06-cec-roles-and-message-policy.md).

[Baseline user interface](20-user-interface.md) owns the visible lifecycle: retain unavailable equipment and stable logical choices, show affected activities before removal, and use the Amity tab for actuator replacement. Ordinary LA churn needs no activity repair. Actual identity/attachment changes require explicit validated mapping. Amity-device names equal their actual hostnames; a network-name change preserves stable hardware and equipment IDs, while main hostname changes use the existing Advanced workflow. No independent location alias or server setup-draft workflow exists.

## Runtime state and loss of connectivity

| State | Authority and permitted behavior |
| --- | --- |
| Active and synchronized | Execute only work admitted by current configuration, coordinator epoch, authenticated connection, and receiver-issued execution lease. |
| Disconnected or coordinator unavailable | Preserve membership and source isolation; cancel remote holds and stop admitting new distributed actions. Keep already established equipment state unless a local safety policy requires an action. |
| Reconnecting | Authenticate pins, exchange current BootIds, reconcile configuration/observations, then obtain fresh leases only for eligible sessions. A TCP connection alone does not restore authority. |
| Enrollment pending | Permit only the bounded enrollment/status behavior in [09](09-membership-security-and-enrollment.md). |
| Retired | Remain isolated and passive; no new proxy claims, activity control, or automatic standalone operation. Reclaim requires physical authorization. |
| Recovery required | Reject distributed execution and expose diagnostic/recovery status. Never guess which saved authority is current. |

On connection loss, cancel held keys promptly using the exact authenticated link/peer/boot/session fence. While the connection and acknowledged plan/route authority remain current, the owning device follows the original completion-paced CEC repeat loop for the admitted down state. There is no per-button lease or renewal requirement; its initial delivery deadline does not shorten an intentional hold. A silent network stall is bounded by general link/plan-authority liveness. A release/cancel path bypasses ordinary queue overload and applies only to its matching hold token. Stop scheduling presses immediately on cancellation, allow an already-started frame to finish, then perform exact cleanup where safe. Do not release a newer hold because an old connection disappeared.

Transport TTL alone is insufficient: a delayed command might otherwise receive a fresh deadline on arrival. Require the receiver-issued execution lease from [08](08-consortium-transport-and-routing.md), bound to the current link, both BootIds, coordinator epoch, configuration, and a receiver-local deadline. Revalidate before the first CEC transmission, not merely at network receipt. Do not compare independent monotonic clocks. A command arriving after its lease expires is stale even if its own `ttl_ms` is large.

The original controller must bound its local user-input queue before planning and preserve causal deadlines into actuator operations. Member-originated user intent, per-button renewal, remote management or input delegation is prohibited. Exact-token cleanup stays bounded and cannot create a new action. Reconnecting discards old operation queues and held states, never replays a missed gesture, and never turns a member into an input gateway.

Reconnection follows [07](07-activity-planning-and-execution.md)'s explicit resumption policy. Persisted `last_requested_sessions` support the UI and Resume action; after coordinator reboot they enter `suspended_after_restart`. Synchronize and observe without automatically waking, routing, or putting equipment in standby. A new Select/Resume intent creates a new SessionId/PlanId after validation. A required member reboot degrades its affected sessions and requires an explicit reconciliation intent; unaffected sessions continue. An ordinary same-boot reconnect may restore fresh-input eligibility after validating current resolved bindings for the same persisted `QualifiedDeviceName` selectors, compatible policy and a sufficiently known route. Automatic unambiguous LA-only re-resolution may advance binding revisions; it does not itself require user confirmation or Select/Resume. Old work remains fenced. Reconnection never replays relative inputs or missed routing steps; independent route uncertainty requires a new Select/Resume intent.

If a node crashed after transmitting a CEC command but before recording its result, the outcome is **unknown**; an acknowledgment journal cannot promise exactly-once execution on external equipment. Query state where the device supports it, or show the uncertainty. Do not repeat a power toggle, key press, or input cycle merely because a network acknowledgment was lost.

Ordinary home-control or BLE input received while its required coordinator is unavailable returns an unavailable result or a clearly bounded local diagnostic response. It does not silently become a second session planner. Local handling still releases keys and enforces previously installed isolation rules.

## Intentional removal

The administrator selects **Remove Amity** on the original controller. Show the affected HDMI adapters, activities, and active sessions before applying the change. Offline status alone never invokes this operation. **20 October 2026 removal amendment:** a responding committed added device receives an explicitly authenticated factory-reset request; an unresponsive device is dropped from the main's roster and requires the user's physical reset button. This does not apply to the main itself.

The removal transaction has these ordered responsibilities:

1. Validate the membership revision and responding target BootId captured by the confirmation dialog. A responding peer without the negotiated reset capability must be updated first; reject before changing membership. For an eligible or offline target, allocate a membership mutation ID and persist a newer membership revision marking it revoked. Remove its ability to originate input/observations, receive new work, or serve as an enrollment relay. Absence from the active allowlist must deny authority even if a diagnostic tombstone has been pruned.
2. Cancel dependent plans and coordinator-side holds, invalidate relevant route/configuration generations, and stop requesting or using that member's receiver-issued execution leases. Closing its operational link invalidates those leases at the receiver; local expiry is the fallback for an unobserved network failure. Other owners reject work whose now-invalid resource/binding assumptions depend on it.
3. If a current authenticated connection exists and the peer supports the negotiated removal-reset contract, send the explicit `factory_reset` membership event over that already established connection. After local revocation, the connection may finish only that exact retirement/reset-result exchange, not ordinary application messages. A disconnected member cannot establish a new active session using its revoked credential. Prepared enrollment cancellation uses its separate abort protocol and never authorizes factory reset.
4. The responding recipient persists `RETIRED`, rejects new work, drains already-started frames and exact matching key cleanup, and disables owned CEC addresses. Only after the actual owner result may it commit the existing factory-reset journal marker. The reset callback checks a short-lived immutable permit for the exact authenticated coordinator, transaction, boots and membership scope immediately before that write. It rejects the main, stale/revoked authority and generic retirement. A management-only committed member may reset without an installed route configuration; any available bound controller identity must match. Return `reset_scheduled` only after the reset marker is durable. Attempt the result transmission, then restart only that target even if the reply is lost. Restart-time journal recovery erases mutable network, settings, configuration, pairings and group state before networking starts; factory commissioning data, firmware and the deliberately retained hardware/Add-code origin remain. CEC isolation remains throughout; no transparent bypass or activity replay is enabled.
5. Keep portable topology references visibly unresolved until the owner deletes or replaces them. Do not silently assign another similarly named source or an OCTOPUS with the same IP address.

There is no shared group private key to rotate when an ordinary member is removed. Its unique credential is simply no longer authorized by the coordinator. Any future credential changes use authenticated pending/commit transitions; no live connection may adopt a different pin because discovery announces one.

Removal is not a remote erase guarantee for an unresponsive member. It may retain its Wi-Fi password, old public roster, and last local CEC role assignment. Its execution leases expire locally and the main rejects it on return, but an unreachable device cannot be erased remotely. Tell the user that it was dropped locally and needs the existing **at-least-ten-second physical factory reset**. A lost result leaves reset status unknown; do not replay the reset or claim that erasure finished. `reset_scheduled` proves only a durable reset decision, not completed physical reboot/erasure. If native drain, journal persistence or the original receiver deadline fails, retain passive retirement and report that reset is unconfirmed; a mere initial Ready indication never bypasses these gates. Before activating a replacement on the same physical domain, disconnect or positively retire the old hardware. If Wi-Fi knowledge must be revoked, change the network credential through the appropriate network administration process.

V1's coordinator-only actuation path limits revocation exposure: other members do not trust the removed member to command them. A future direct peer overlay would need an explicit stale-roster policy and cannot promise immediate revocation during a partition. This limitation is a reason not to invent all-to-all trust in the first release.

Deleting a Matter fabric, removing a HomeKit pairing, unpairing a remote, generic membership fencing, enrollment abort and authority loss remain separate actions and never invoke this reset path. **Remove Amity** deliberately combines roster revocation with factory reset only for the selected responding added device. The main's separate Advanced factory-reset command and the physical reset button retain their existing explicit authorization. See [12](12-control-surfaces-and-admin.md) and the pinned [Matter administration](https://github.com/retsyx/amity-esp32/blob/d50af8026938797fc0820d0107f4c4e064c2d2bc/components/amity_matter/amity_matter.cpp) and [remote bond handling](https://github.com/retsyx/amity-esp32/blob/d50af8026938797fc0820d0107f4c4e064c2d2bc/components/ble_remote/ble_remote.cpp).

## Replacement and recabling

**Replace Octopus** should preserve the owner's logical system while assigning fresh hardware identity. Revoke the old member, enroll the new board with its own `OctopusId`, operational key, and setup code, and map the old attachment roles to explicit new `TentacleId`/side endpoints. Preserve persistent `ComponentId` and `ActivityId` only where the owner confirms the equipment is the same. Never clone a private key, BLE bond database, Matter Node ID, or HomeKit identity to make replacement appear transparent.

That approved mapping rewrites the affected qualified OSD-name prefixes to the new octopus/tentacle/side while retaining the selected OSD names where verified. Clear old resolved-address caches and rediscover current LAs. Board replacement is a semantic attachment change; ordinary address churn on the existing attachment is automatic runtime resolution and must not enter this replacement workflow.

The candidate starts quarantined for routing until its board profile, port orientation, discovered devices, domain membership, and proxy identity capacity have been validated. A changed cable can merge previously independent CEC domains. That may put a real TV at logical address 0 beside a proposed virtual-TV role, or consume the last usable playback address. Quiet traffic is not proof that the domains are separate.

Stage one configuration/binding transaction, then activate its new revision after all affected owners acknowledge readiness. Invalidate old binding/domain revisions and execution leases. An unavailable old owner is not permission to reuse its electrical role while it is still attached. Tests must include replacement with swapped front/back wiring and accidental domain merging; see [05](05-discovery-and-topology.md).

Actuator replacement does not transfer the original controller, remote or integration gateway. Failed-main recovery is a separate supported manual workflow: fresh replacement hardware completes Matter BLE setup and restores portable configuration, with explicit old-main isolation, new authority and re-pairing/re-enrollment. It never clones ecosystem or remote pairing identity.

## Fixed original controller: no handover or member promotion

The 20 October 2026 amendment removes the former Move coordinator and successor workflow. The original first-setup Amity retains all planning, browser/admin UI, sole remote and home-integration roles. Added devices are actuators only. No API, imported snapshot, old handover artifact, larger epoch or valid member certificate authorizes promotion. Old transfer-marker presence forces passive recovery; there is no decoder, successor state machine or transfer API. [SC-01–SC-08](21-original-controller-policy.md)

## Unplanned loss of the original controller

Actuators keep physical/source isolation, finish already-started frames and release/expire exact held keys, then stop new positive control. They expose no hosted UI or integration fallback. Repair or restore the original controller while preserving its stable identity and credentials; synchronized observations do not replay old activity or input queues.

If the original main fails, the user may physically replace it, complete fresh Matter BLE main setup, and upload a saved configuration using the existing **Advanced → Upload/Restore** interface. Explicitly confirm that the old main is offline/isolated. Preserve logical component/activity IDs, names/order and portable slot/alias choices; all imported activities initially remain disabled because executable routes/bindings/resources, remote assignment, PA evidence and old member domains are discarded. Fresh Scan HDMI and the original Edit/Save repair supported direct paths; unsupported receiver/switch paths remain ACT-01 work. The new hardware establishes its own durable main role and new trust; backup data cannot replace a controller inside an already-live installation.

Re-pair the sole remote and Matter/HomeKit associations. Factory-reset every old headless member using the existing **at-least-ten-second** physical button hold, then open the **three-to-below-ten-second** candidate window and re-add it under the replacement main. An unreset member cannot reopen enrollment. Reset clears Wi-Fi, fabrics, bonds and group operational state but retains the origin hardware ID and Add-code verifier; re-add uses fresh TLS keys/leaf and new trust, not the old roster, certificates, prepared plans or leases. Never copy private keys, bonds, integration identities or credentials. Restore itself does not wake, route, repeat input or resume activity. A returning old main must stay isolated or be explicitly reclaimed, and cannot command the new installation. This supported manual recovery is not promotion, an election, planned transfer or automatic failover. [SC-08 and detailed steps](21-original-controller-policy.md#manual-main-replacement-from-a-configuration-backup)

## Reset, bootstrap loss, and credential changes

Factory reset must include every new membership, operational-key, prepared-join, handover, transport-ticket, and configuration-authority record in the durable reset plan. Retain the immutable factory setup record and the deliberately reset-retained `amity_origin` identity/verifier. The baseline reset mechanism already journals cleanup and performs restart-time recovery; extend it rather than adding an unrelated best-effort erase loop. See pinned [factory-reset implementation](https://github.com/retsyx/amity-esp32/blob/d50af8026938797fc0820d0107f4c4e064c2d2bc/components/device_settings/factory_reset.cpp) and [settings persistence](https://github.com/retsyx/amity-esp32/blob/d50af8026938797fc0820d0107f4c4e064c2d2bc/components/device_settings/device_settings.cpp).

A reset inline board starts in a safe unclaimed configuration. It must not immediately claim a virtual-TV identity, execute a saved route from an obsolete snapshot, or announce itself as a new standalone controller. Explicit local configuration/enrollment activates those roles. Membership reset does not erase the board's physical isolation boundary.

The printed bootstrap code may remain valid across reset because its verifier is retained, but it still requires a new physical enrollment window. Loss/disclosure of the code uses physically authorized verifier rotation; changing an administrator password or Matter PIN does not rotate it. Buttonless hardware uses the documented USB-assisted path rather than bypassing presence checks.

An ordinary operational credential update must prove possession of the new key, prepare the new certificate/pin durably, establish a new authenticated connection, and commit before retiring the old credential. Bound any overlap to that transaction and reject both old-session actions and late update messages after completion. V1 may expose this as re-enrollment if an in-place update is not implemented. Changing the original controller credential must preserve its stable controller ID and use authenticated durable pin-update/fencing transitions. It cannot nominate another board or enable a member UI; changing the web certificate is unrelated.

## Required failure tests and implementation dependencies

Integrate this lifecycle with MembershipStore, GroupService/SystemControl, the reset journal, local policy snapshots, and configuration revisions. No individual component may “repair” a missing record by creating a new authority automatically. Invalid/corrupt authority state enters recovery-required mode with a diagnostic reason.

Acceptance tests must cut power before and after every enrollment/removal/reset-marker commit; reject legacy handover/promotion attempts; lose/duplicate/reorder every acknowledgment; hold a member offline throughout removal; restore an old coordinator after recovery; and restart a prepared member with no reliable wall clock. Explicit removal-reset tests must reject main/self targets, unauthenticated or stale transactions, generic retire and enrollment abort, prove native drain before the marker, preserve retained origin/factory/firmware through reset interruption, and restart after a result transmission failure without applying a second reset. Management-only committed members and unsupported old peers require explicit coverage. Assert that at most one committed coordinator can issue accepted work and that stale execution leases cannot revive an old route. Exercise unknown CEC outcomes, key-release deadlines under queue pressure, replacement while old hardware remains attached, domain merges, and reset halfway through namespace erasure. Use independently clocked simulated OCTOPUSES as well as hardware tests; a singleton fake worker cannot demonstrate these properties. [15](15-validation-and-release-gates.md) owns the complete validation matrix.
