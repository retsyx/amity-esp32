# 09. Membership security and enrollment

**20 October 2026 controller-policy amendment:** [Original controller and subordinate devices](21-original-controller-policy.md) is normative. The original first-setup Amity alone hosts the UI/integrations and sole remote; added devices are UI-less actuators, never input gateways or successor controllers.

## Purpose and status

This is a proposed implementation contract, version 0.1, against Amity commit `d50af8026938797fc0820d0107f4c4e064c2d2bc`. It defines how an OCTOPUS becomes an authorized CONSORTIUM member. The feature is not present in that baseline. The words MUST and SHOULD describe requirements of this proposal.

V1 uses a designated coordinator as both membership authority and desired-state coordinator. These are separate logical responsibilities even when one MCU implements both. Members initiate authenticated connections to that coordinator; membership does not authorize arbitrary member-to-member commands. The roster distributed for administration is authenticated by its coordinator connection, not a transferable delegation credential. A later peer overlay requires a separately designed signed roster, resource authorization, revocation distribution, and partition policy.

This document owns bootstrap credentials, enrollment transactions, operational identities, and authorization. [10](10-ble-and-matter-coexistence.md) owns radio and Wi-Fi integration; [08](08-consortium-transport-and-routing.md) owns the operational wire envelope; [13](13-faults-removal-and-recovery.md) owns retirement and recovery. [20](20-user-interface.md) defines the baseline interface; its user-facing sequence does not replace the security requirements here.

## Identities and trust boundaries

| Item | Purpose and lifetime |
| --- | --- |
| `OctopusId` | Persistent random 128-bit hardware identity, formatted as 32 lowercase hexadecimal digits. Neither a MAC address nor a Matter Node ID. |
| `ConsortiumId` | Identifies one local system, including a singleton. Joining an existing consortium replaces the candidate's isolated singleton association. |
| Bootstrap code | Independent random 128-bit enrollment secret, presented as QR/manual base32 with a checksum. Never the Matter PIN, HomeKit PIN, admin password, or BLE bond key. |
| Bootstrap verifier | Versioned Security2 username, salt, and SRP verifier stored on the candidate; the setup code is held by the owner. Treat the verifier as sensitive. |
| Operational credential | Locally generated P-256 private key and self-signed leaf certificate, separate from the web HTTPS certificate. Private keys never leave their OCTOPUS. |
| Membership record | Coordinator ID and certificate/pin, consortium ID, role, membership revision, coordinator epoch, and transaction state. |

The baseline factory record is version 3 and has no consortium bootstrap identity. Its reserved area is not a place to append this feature silently. On the first supported boot, migration durably initializes `OctopusId` in the reset-retained, versioned `amity_origin` record in `amity_cfg`. Enrollment remains disabled until an authenticated administrator session plus physical authorization adds the bootstrap salt/verifier, preserving that ID. The owner sees the newly generated code once; the origin retains the ID and verifier, not a recoverable copy of the raw code. Factory-v4 provisioning is a separate explicit operation. The format and reset allowlist are owned by [11](11-config-storage-and-migration.md). Existing Matter credentials remain independent. See the pinned [factory credential parser](https://github.com/retsyx/amity-esp32/blob/d50af8026938797fc0820d0107f4c4e064c2d2bc/components/device_settings/include/factory_credentials.hpp) and [Matter credential adapter](https://github.com/retsyx/amity-esp32/blob/d50af8026938797fc0820d0107f4c4e064c2d2bc/components/amity_matter/commissioning_credentials.cpp).

The threat model includes an untrusted LAN, spoofed mDNS advertisements, nearby BLE devices, captured/replayed traffic, stolen setup codes, and an ordinary member attempting coordinator-only operations. It also includes crashes during enrollment. A compromised coordinator can issue authorized system commands; a compromised member can misreport its own CEC observations and disrupt equipment it physically controls. Membership encryption cannot make those reports truthful. Physical extraction protection requires the production boot/storage gates in [14](14-ota-and-compatibility.md); mTLS is not firmware attestation.

## User experience and physical authorization

The first OCTOPUS uses the existing Matter commissioning path to obtain Wi-Fi, entered through the physically authorized first-board policy in [10](10-ble-and-matter-coexistence.md). Its local administration page manages the initial singleton consortium and enables adding members. Do not allocate a second consortium ID merely because that page is first opened. A custom phone app is not required. A new candidate may join that consortium without joining any Matter fabric or opening a separate administration session on that candidate.

For each subsequent OCTOPUS, the owner selects **Add Octopus**, scans or locally imports its consortium code image, or enters the manual code, and opens its physical enrollment window. The coordinator automatically selects itself or an eligible nearby enrolled member as the BLE helper; the normal flow does not ask the user to choose a relay. Radio availability and bounded discovery determine eligibility, while the authenticated bootstrap exchange determines identity. No browser Bluetooth API is required.

When the candidate needs network credentials, default to transferring the system's already available credentials for a supported, tested Wi-Fi mode through the authenticated enrollment session. Do not require retyping those credentials or expose them to the browser. Preserve an already networked candidate's network; an unavailable credential or unsupported network mode needs an explicit supported setup path, not a silent network replacement. Adding a member does not require another Matter accessory pairing or candidate administration login.

The page distinguishes **Connecting to Wi-Fi**, **Finishing enrollment**, and **Enrollment ready**. Discovering an advertisement or completing a BLE exchange is insufficient to show Enrollment ready; the durable transaction and normal synchronization below must finish. Equipment readiness is a separate result of tentacle/topology validation and named-function tests. Add requires a **Name** before enrollment. Normalize and validate it using the existing hostname rules: 1–32 ASCII letters, digits or hyphens, with no leading or trailing hyphen, stored in canonical lowercase form after trimming surrounding whitespace; internal spaces/punctuation are invalid, not slugified. The admitted name sets the candidate's actual persistent hostname through the authenticated enrollment transaction; it is not an optional cosmetic location alias. Report enrollment success only after the agreed name is applied. Naming never changes the candidate's stable OctopusId, configured equipment selectors or operational authorization.

The proposed consortium window lasts 180 seconds and does not extend in response to unauthenticated traffic. For supported retail button profiles, [10](10-ble-and-matter-coexistence.md) defines distinct physical actions: a debounced short release before 3 seconds opens initial Matter setup only on an eligible fresh/unconfigured singleton; a release after at least 3 seconds and before 10 seconds requests consortium enrollment; reaching 10 seconds follows the factory-reset path. A longer hold must never first enter either shorter setup mode. The hardware profile supplies exact printed/UI instructions and indicator behavior where supported. Current buttonless hardware needs USB-assisted physical authorization; an administrator password alone is not a substitute. These are proposed hardware/UX release requirements, not existing capabilities of every board. See the pinned [reset policy](https://github.com/retsyx/amity-esp32/blob/d50af8026938797fc0820d0107f4c4e064c2d2bc/components/device_settings/reset_button.cpp) and [device settings notes](https://github.com/retsyx/amity-esp32/blob/d50af8026938797fc0820d0107f4c4e064c2d2bc/components/device_settings/README.md).

An already enrolled candidate requires an explicit physically authorized leave/reclaim operation before joining a different consortium. It must not switch groups because somebody supplied its printed code. A lost or disclosed legacy code can be replaced through the same physical recovery path; rotate the verifier, invalidate the old code, and retain the `OctopusId`.

Browser trust remains separate. The existing server uses a locally generated self-signed certificate. Operational mTLS does not remove a browser warning, prove that an unverified web page is the intended board, or make camera APIs universally available. A usable first-browser trust procedure remains an explicit product gate; neither the printed URL nor this enrollment protocol solves it. Keep manual code entry and local image import available, and never advise disabling browser verification globally. See [12](12-control-surfaces-and-admin.md) and the pinned [web credential implementation](https://github.com/retsyx/amity-esp32/blob/d50af8026938797fc0820d0107f4c4e064c2d2bc/components/web/credentials.cpp).

## Enrollment transaction

Only one candidate transaction is active at an enrollment actor. The current bootstrap profile is **2**; its authenticated proposal requires `candidate_hostname` in canonical lowercase DNS-label form. The name and profile are included in the canonical proposal digest, so retries cannot substitute another hostname. A profile-1 candidate cannot silently ignore the new required name; update it through a compatible supported path before induction. The coordinator allocates a random 128-bit `join_id`. Protocol, bootstrap-profile, and configuration versions are separate numbers. Bootstrap discovery carries only service/version hints and a nonsecret identification suffix; it carries no password, Wi-Fi credential, or trusted operational pin.

1. **Authenticate the bootstrap session.** The coordinator is the Security2 SRP client and the candidate is its server. Both verify the PAKE proofs. Reject unsupported profiles; do not fall back to Security0, an unauthenticated key exchange, or an empty proof.
2. **Bind the proposed membership.** Inside the authenticated encrypted session exchange `join_id`, both OCTOPUS IDs, consortium ID, coordinator epoch, proposed member role, membership revision, protocol range, both leaf certificates and their SHA-256 SPKI fingerprints, bootstrap profile 2, and the required canonical `candidate_hostname`. Check certificate identity/profile and the ID printed in a QR, when supplied. Canonically encode and hash this proposal into `join_digest`; authenticate the digest in subsequent steps. No field is inferred from a BLE name or IP address.
3. **Prepare durably.** The coordinator stores `PREPARED`, including the candidate's provisional credential and digest, before asking the candidate to persist its matching record. The candidate durably validates/applies the agreed hostname before Wi-Fi staging and acknowledges only after its storage commit. Provisional trust grants enrollment/status operations alone.
4. **Establish network reachability.** Transfer credentials only within Security2, when the candidate needs them. Use the existing Wi-Fi owner and the commit rules in [10](10-ble-and-matter-coexistence.md). An existing network is not silently replaced. Wi-Fi success and consortium membership are separate durable results.
5. **Prove the LAN path.** The candidate opens the operational mTLS connection to the coordinator, verifies its prepared credential, and supplies `join_id`, `join_digest`, and the coordinator's fresh challenge response. Both TLS endpoints prove possession of the keys exchanged through PAKE. The provisional connection accepts only Hello and enrollment finalization/status/abort messages; it cannot submit inputs, obtain operational execution leases, or actuate CEC.
6. **Commit authority.** After that round trip, the coordinator persists the membership revision as committed with `ready=false`, then sends the idempotent commit result. The candidate persists `ACTIVE` before acknowledging. The coordinator marks it ready only after that acknowledgment and normal capability/configuration synchronization. [08](08-consortium-transport-and-routing.md) still requires an execution lease before actuation.
7. **Close bootstrap access.** Erase PAKE/session secrets from memory, stop the enrollment advertisement, and release the radio reservation. Preserve only the journal and credentials needed for operational service or recovery.

| Durable state | Permitted behavior after restart |
| --- | --- |
| No prepared record | No consortium authority; new bootstrap exchange needs a new physical window. |
| `PREPARED` | Resume only the same pinned transaction over LAN; do not reopen BLE automatically or accept a different authority. |
| Coordinator committed, candidate pending | Reissue/query the same commit. Do not roll back the membership merely because an acknowledgment timed out. |
| Candidate active, acknowledgment lost | Reconnect, verify the coordinator, and repeat status/acknowledgment idempotently. |
| Aborted before commit | Remove provisional trust and secrets; delayed messages for that transaction are rejected. |
| Cancellation after commit | Perform explicit removal at a newer membership revision; an enrollment timeout cannot undo committed authority. |

Journal writes use [11](11-config-storage-and-migration.md)'s atomic persistence contract. After a browser refresh or new login, recover progress from that durable transaction and offer **Resume** or **Remove pending member**; do not rerun completed steps or allocate a second member. A prepared transaction that can resume over its pinned LAN path does not require the setup code again. A new bootstrap attempt still requires its physical window and code; raw setup codes must not be retained in persistent browser storage to make retries easier. Cancellation follows the transaction's durable pre-commit or post-commit state, not the last progress text the browser saw. The UI must not claim a disconnected candidate was erased. A pending node can retain successfully committed Wi-Fi while having no consortium control authority. No wall-clock expiry is required to resume an already authenticated, fixed transaction; its narrow authorization is the safety boundary. Fresh PAKE windows remain bounded by a local monotonic deadline.

### Restricted LAN message contract

Use [08](08-consortium-transport-and-routing.md)'s `enrollment_control` kind after Hello, with closed payloads containing `phase`, `join_id`, and `join_digest`. The digest is SHA-256 of the canonical prepared proposal, encoded as 64 lowercase hexadecimal digits. It is an authenticated equality check, not a substitute for PAKE or TLS.

| Phase | Direction and additional fields |
| --- | --- |
| `challenge` | Authority → candidate; fresh random 128-bit `challenge_nonce`, encoded as 32 lowercase hexadecimal digits and valid only on this TLS link. |
| `prove` | Candidate → authority; echoes that nonce after validating the prepared digest. |
| `commit` | Authority → candidate; committed `membership_revision` and `ready=false`. |
| `ack` | Candidate → authority; persisted membership revision and `state=active`. |
| `status` | Either side; `request` boolean. Responses carry `state` from `prepared`, `committed`, `active`, `aborted`, `unknown`; committed/active responses also carry the recorded membership revision. |
| `abort` | Either side before commit; `reason` from `cancelled`, `incompatible`, `network_failed`, `internal_error`. A committed result requires retirement instead. |

All identities/epochs remain subject to the envelope and prepared-record checks. A new TLS link receives a new challenge. An unknown transaction does not allocate trust or create a member. Commit/status retries return the durable result; they do not generate a new revision. Implement the matching closed schemas before enabling these phases.

## Enrollment through a nearby member

The coordinator grants a currently authenticated member a bounded relay reservation, tied to the current TLS session, coordinator epoch, `join_id`, and candidate hint. That helper owns the local BLE central connection and forwards opaque Security2 request/response records over its existing coordinator connection. The PAKE endpoints remain the coordinator and candidate. The helper receives neither the setup code nor plaintext Wi-Fi credentials and cannot replace authenticated identities.

A relay is permitted only after an authenticated Add Octopus operation. It has one BLE candidate and one request/response in flight; no arbitrary TCP proxy, Internet destination, generic GATT tunnel, or indefinite scanning permission. Proposed limits are a 180-second reservation, 4,096-byte complete bootstrap record, and one bounded reassembly buffer per active endpoint. Disconnect, revoked membership, expired reservation, or coordinator change cancels it. Relay failure before commit leaves a resumable pending transaction or a clean abort; it does not create membership.

## Security2 compatibility and implementation gate

Reuse the pinned ESP-IDF Security2 server/protocomm processing through a custom shared-host GATT transport. Do not start its separate NimBLE provisioning host. Security2 uses SRP-6a with a 3,072-bit modulus, generator 5, SHA-512, and AES-256-GCM. Its server expects a 384-byte client public value and a 64-byte proof. The precise protocol is the pinned [Security2 implementation](https://github.com/espressif/esp-idf/blob/fff9895c82d744c7237be8847347bdd1b07c6643/components/protocomm/src/security/security2.c) and [SRP implementation](https://github.com/espressif/esp-idf/blob/fff9895c82d744c7237be8847347bdd1b07c6643/components/protocomm/src/crypto/srp6a/esp_srp.c).

Neither that C SRP interface nor Amity's vendored HomeKit `mu_srp` supplies the needed embedded client. The HomeKit server also hashes a one-byte generator in its M1 calculation, whereas this Security2 implementation hashes the generator padded to the 384-byte modulus width. Matching algorithm names therefore do not imply wire compatibility. Do not modify HomeKit proofs, reuse its verifier, or claim its implementation is a drop-in client. See the pinned [HomeKit SRP source](https://github.com/retsyx/amity-esp32/blob/d50af8026938797fc0820d0107f4c4e064c2d2bc/third_party/esp-homekit-sdk/components/mu_srp/mu_srp.c).

The implementation gate is a reviewed embedded Security2 client with exact byte-level vectors: username/password normalization, salt, padding, leading zeros, invalid public values, zero scrambling parameter, both proofs, and GCM counters. Define one bootstrap-profile encoding in the provisioning tool; presentation separators/checksums must not accidentally enter the password derivation. Limit failed proofs and stalled sessions independently of the overall window; the initial policy closes a window after five failed proofs. Rate limits must protect local CEC/remote deadlines, not merely slow password guessing.

The pinned GCM state uses an 8-byte session identifier and a 32-bit counter, advanced on each encrypt/decrypt operation. Reassemble an entire record before passing it to Security2. Serialize request/response processing; duplicates must return a cached ciphertext response without consuming the counter again. An uncertain exchange can restart the PAKE session rather than guess the counter. Reject counter wrap, conflicting fragments, oversized records, and late records from an old connection. Crypto and protobuf processing run outside GAP/GATT callbacks.

## Operational mTLS and offline cold boots

Use a dedicated operational TLS configuration with certificate authentication required in both directions. The proposed interoperable floor is TLS 1.2 with ECDHE-ECDSA and AES-128-GCM/SHA-256; disable older TLS, static-key-exchange, anonymous, and CBC suites. TLS 1.3 with the matching P-256 signature policy and AES-128-GCM/SHA-256 may be enabled only after the pinned build passes interoperability/resource gates. During enrollment, store the explicitly exchanged self-signed leaf DER as a local trust anchor **and** its SHA-256 SPKI pin and expected OCTOPUS identity. The coordinator holds active/provisional member entries; each member trusts its designated coordinator. Ordinary public CA trust, mDNS, another member's certificate, or membership in the same Matter fabric is insufficient.

The v1 certificate profile is one P-256 leaf, `CA=false`, digital-signature usage, client/server authentication usages, and a DNS SAN derived from the stable ID, for example `o-<OctopusId>.amity.invalid`. This name is a certificate identity, not a discovery address. A TLS client supplies the expected name explicitly; a server maps the authenticated certificate to its enrolled identity. Cap leaf DER at 1,024 bytes, validate its self-signature/profile during enrollment, and reject unexpected chains or malformed extensions. Certificate replacement, even with the same key, is an authenticated credential-update transaction; unknown replacement certificates are not adopted automatically.

Operational authorization deliberately depends on explicit pins and membership revision, not Internet time. In this dedicated context only, a verification callback may mask the certificate's `FUTURE`/`EXPIRED` time flags **after** confirming the exact enrolled leaf, pin, identity, and permitted membership state. All other failures remain fatal. This policy applies consistently before and after time synchronization, so a cold boot cannot create a temporary trust downgrade. Revocation and rotation replace calendar expiry for these private operational credentials. Web HTTPS, OTA validation, and other TLS contexts retain their own normal policies.

This has a concrete SDK path: pinned Mbed TLS supports an exact locally trusted end-entity certificate and `mbedtls_ssl_set_verify`/`mbedtls_ssl_conf_verify`. `VERIFY_REQUIRED` additionally requires a configured trust-anchor list or CA callback; an ordinary callback alone is insufficient. Never set `VERIFY_NONE`, clear every verification flag, or accept a key merely because the clock is unset. See pinned [leaf trust handling](https://github.com/espressif/mbedtls/blob/a2b32072ea898afc1ed5b6caf6931e36028c91d6/library/x509_crt.c), [TLS verification](https://github.com/espressif/mbedtls/blob/a2b32072ea898afc1ed5b6caf6931e36028c91d6/library/ssl_tls.c), and [verification APIs](https://github.com/espressif/mbedtls/blob/a2b32072ea898afc1ed5b6caf6931e36028c91d6/include/mbedtls/ssl.h).

Authentication does not bypass authorization. Members have only actuator/observation scope and bounded explicitly authorized bootstrap relay scope. No roster/configuration flag can grant them user-input, remote ownership, UI/admin hosting, home-integration or coordinator authority. Only the immutable original controller issues plans, configuration and retirement. A synchronized actuator issues receiver-local execution leases only to that controller; it never obtains ingress leases for user input. A candidate's existing Matter fabric or saved remote bond is retained but disabled after adoption. Disable TLS early data/session resumption unless current pins/roles are rechecked; a fresh mutual handshake is the simple default.

## Implementation work and acceptance criteria

Implement separate `BootstrapIdentityStore`, `EnrollmentService`, `MembershipStore`, and `OperationalTlsVerifier` responsibilities. Integrate origin/reset policy with `device_settings`, user actions with `web_admin`, networking with `amity_matter`, and transport authorization with GroupService. These are proposed boundaries, not existing class names.

Release requires interoperable SRP vectors and hardware memory measurements; power interruption at every journal boundary; wrong-code/pin/ID/role rejection; cold boot without Internet time; expired-but-exact enrolled leaf acceptance under the documented policy; unknown or revoked leaf rejection; relay substitution/replay failure; malformed-fragment limits; and proof that no CEC command is accepted before durable enrollment, configuration synchronization, and a current execution lease. Sanitized logs expose transaction IDs and failure stages, never setup codes, passwords, private keys, SRP secrets, or full credential payloads.
