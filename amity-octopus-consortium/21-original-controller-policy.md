# Original controller and subordinate devices

Amendment dated **20 October 2026**, requested after the 0.1.60 implementation audit. This is a normative scope change, not a claim that the historical firmware or tests already enforce it. It supersedes earlier permission for member input gateways, one remote per member, remote-owner moves, member-hosted administration, and planned coordinator promotion/handover. ## Original algorithms and functionality amendment — 21 October 2026

The user requires the current `main` implementation as the behavior source of truth; this merge uses `98e64a6`. Its independent key lifecycle, asynchronous CEC submission, `wait_for_release` and Siri macro handling supersede the older `d50af8026938797fc0820d0107f4c4e064c2d2bc` behavior where they differ. Distribution layers ownership and message transport onto the same code. It MUST have zero effect on CEC behavior: equivalent local and remote inputs produce the same frames, order, attempt budgets, admission results and key/repeat/release lifecycle at the owning wire. This requirement applies to implementation, specifications, tests and future maintenance, and supersedes conflicting older proposals. The repository-wide instruction is [AGENTS.md](../AGENTS.md).

Preserve activity/AVR/audio/switch behavior, discovery and physical-address algorithms, remote semantics, CEC transmission/retry behavior, held-button repetition and baseline UI workflows. Distributed authority, boot, binding and route fences prevent stale or unauthorized work; they do not authorize a replacement normal-operation algorithm, repeat cadence, timeout or recovery policy. Compare the relevant baseline source and tests before changing existing behavior. Record each necessary distributed adaptation and its parity evidence in the owning document. Previously approved user amendments, including this document's fixed-controller/headless policy and [the UI amendments](20-user-interface.md), remain in force.

The user explicitly applies this rule to **Siri remote swipes** as well. Preserve the original gesture recognition, thresholds, direction/acceleration behavior, timing, generated press/release sequences, cancellation and activity-generation handling. The consortium delivers the original resulting events to the selected owner; it does not reinterpret swipes, replace the gesture algorithm or convert taps into sustained holds. Compare local and remote target behavior with the same baseline input traces.

Devices exchange button **state changes**. Each held key has its own state and at most one outstanding attempt. Its successful completion permits only that key's next press. Newly received keys and other CEC commands submit immediately without waiting for any earlier ACK, transmission completion or capacity. Input, replies, setup and discovery continue while frames are outstanding; CEC still serializes frames on each physical wire. Releasing Right while Volume Up is held stops only Right. Normal key-up does not invalidate a shared cancellation generation or cancel already admitted frames. There is no repeat timer, repeat backlog, periodic remote press or per-button renewal. A tap remains finite. General authenticated connection/plan liveness fences distributed ownership. [Execution details](07-activity-planning-and-execution.md).

`SystemControl` preserves one exact hold token per logical key, rather than one shared remote hold. Aliased physical buttons share that logical hold until their last release. The same `RemoteInputController` implements startup/accepted-selection `wait_for_release` for local and remote equipment, including same-target selections, all-buttons-up clearing and the one-second fallback without replay. Rejected selections and long-Power repair do not arm it. Siri alone supports the fixed Power+Select/Up/Right/Down/Left defaults: activity 0–4 for selector holds below 500 ms, 5–9 at or above 500 ms, executed on the first release of either macro button and consumed until all physical buttons are up. Transport does not reimplement or alter these input policies. [Input contract](../components/ble_remote/README.md).

## Executor and CEC boundary amendment — 21 October 2026

The executor owns button state and decides which messages to send, including completion-paced held repeats and implicit end-of-stream releases. It MUST NOT buffer outgoing messages. It validates and translates each decision, then submits directly to the CEC layer; a full queue reports failed admission rather than creating an executor backlog. It may retain exact button/target/fence state and completion bookkeeping, which must not become a queue of messages awaiting submission.

The CEC layer owns the only outgoing-message FIFO: **eight normal message slots plus one release-only overflow slot per CEC wire**, with independent front/back wires. Count queued and active messages together. At eight messages, ordinary submission rejects but one executor-selected release may become message nine. At nine, further release submissions are **dropped**, with no executor capacity retry or retained release backlog. Normal release submissions also consume the ordinary slots when space exists. Finite batches are all-or-busy: a press may fill slot eight and its final release slot nine, but a press can never occupy slot nine.

CEC remains a mechanical transmitter: send the supplied frames with the supplied attempt budget, perform the wire protocol and report the result. The executor explicitly marks a release as eligible for the one overflow slot; CEC applies that generic admission instruction without interpreting opcodes. It MUST NOT decide button state, produce a repeat or release, or choose other semantic messages. Release messages are requested by the executor; “CEC owns the queue” does not grant it release authority. Existing supplied wire-attempt budgets remain distinct from the prohibition on retrying admission of a dropped release.

The user's subsequent clarification permits queues where necessary for **communication between threads/tasks**, while prohibiting their use to buffer work. Bounded IPC handoff of physical input state, typed owner requests or authenticated socket-worker envelopes is distinct from an executor transmit buffer. Ordinary full admission rejects immediately; do not retain ordinary semantic work for a later CEC-capacity retry or accumulate repeat events. Preserve causal down/up ordering and exact failed-key no-op handling under IPC pressure. The specified single CEC overflow slot replaces proposals to add another control-work buffer.

The user explicitly removes key-press retries: each `User Control Pressed` (`0x44`) frame has **one wire attempt**, including finite taps and key frames used by other original algorithms. Intentional held repetition remains a distinct executor decision after successful completion. A failed key transmission ends that key's pressed state and stops its repetition. A later matching button-up is a no-op; unchanged down reports, authority renewal and policy refresh cannot restart the stopped key. A fresh up/down sequence is required to start again. These are deliberate exceptions to the baseline's admitted-NACK continuation and ordinary key-frame retry behavior.

`User Control Released` (`0x45`) has no key operand: release is global for its receiving CEC device. The executor MUST derive release from the end of that device's press stream, after one or more presses, when **all** its keys are no longer pressed. A remote key-up only updates the matching key state; it does not map directly to a release frame. Completing a finite tap, cancellation, or a last-key TX failure can also end the stream. Ending one key while another remains pressed MUST NOT emit release. Aggregate by physical CEC wire, initiator and destination; unrelated recipients and wires continue independently. Preserve exact binding/boot/authority fences for cleanup; never redirect an old release to a newly bound appliance.

When the final key ends, submit its release immediately into CEC's FIFO behind admitted presses, without waiting for their ACK, completion or first edge. Later positive work cannot overtake that admitted release. A never-started, canceled press alone does not establish a wire stream needing release. An isolated finite tap may atomically submit press plus final release to the sole CEC FIFO: its implicit end is already known, and a generic first-edge dependency suppresses the release if the press never starts. A finite tap joining another held key's stream submits its single press without an unconditional release. These rules retain the original finite Siri sequences without releasing another active key.

Keep end-of-stream cleanup as semantic state, separate from ended key tokens, only until its final release can be ordered after admitted presses. Consume that decision when submission is attempted: it may use slot nine, but rejection at nine drops it permanently. Do not regenerate it when capacity opens, from a later key-up, or from authority refresh. Record a dropped/uncertain release separately from successful wire delivery. These rules supersede the earlier button-up-only, failure-without-release, eight-slot hard-cap and release-admission-retry interpretations.

## Fixed original controller

The same firmware image serves both roles; there is no original-only or actuator-only build. A freshly provisioned device has no Wi-Fi network and MUST NOT open a hosted UI, start HomeKit, or connect to a remote. Network credentials arrive only through Matter BLE enrollment for the original controller or the authenticated Amity BLE enrollment channel for an added device. A physical setup gesture exposes the appropriate bounded bootstrap opportunity, not a browser setup page.

Successful Matter commissioning, with committed fabric and checked Wi-Fi credential persistence, is evidence for a durable original-role compare-and-set. Connecting to Wi-Fi, receiving an uncommitted fabric, or merely beginning a BLE session is insufficient. Authenticated member preparation must durably select headless operation before acknowledging adoption. Competing or delayed enrollment cannot change a committed role. The role is stored independently of Matter fabric count, so removing the last home association does not turn the original into an unclaimed device or promote an actuator. On reboot, stored role is resolved before any user-facing service starts; ambiguous state stays passive. Retained legacy configurations may establish the original only from proven durable original authority or checked, fully committed Matter/network state.

The Amity device used for first system setup remains the **original controller** for that live installation. It is the only activity planner, membership/configuration authority, remote owner, browser/admin host, and Matter/HomeKit integration gateway. Its stable internal `OctopusId` is recorded explicitly as `controller_octopus_id`; it is not inferred from an array position, label, hostname, IP address, discovery order, uptime, or a peer's claimed epoch. Renaming, adding/removing devices, ordinary configuration restoration and changing a screen do not change it. Manual recovery onto freshly enrolled replacement hardware creates a new installation authority, as specified below; it is not a live controller-ID edit.

Every added Amity device is strictly a subordinate **actuator**. It may provide scoped equipment observations, execute guarded semantic CEC work from the original controller, preserve local source isolation, and run the authenticated enrollment/configuration/update/retirement channel. A separately authorized bounded enrollment helper may relay bootstrap bytes; that permission never grants input or controller authority.

Explicit removal by that original controller factory-resets a responding committed added device through its existing durable reset journal, after native retirement drains and before the target-only restart/result-attempt boundary. An unresponsive device is dropped locally and requires a physical reset. Generic retirement, authority loss and enrollment cancellation do not reset a device. The original main itself is never a target of this member-removal path. Reset leaves the device unclaimed with no UI or automatic enrollment/activity authority; retained factory/origin material supports a later physically authorized setup. [Removal details](13-faults-removal-and-recovery.md#intentional-removal).

Added devices MUST NOT host any UI: no normal web app, login/setup/admin page, recovery/status page, independent activity controls, or Matter/HomeKit accessory/control surface. Status, setup, configuration, update and removal are accessed through the original controller. Explicit physical/USB bootstrap and recovery remain available where required; they are not a second hosted UI. Enrollment must durably select the subordinate startup mode and cancel/drain prior control or setup work before acknowledging the role. An existing local UI or integration must not remain active after adoption.

## One remote, multiple screens

At most one supported BLE remote is paired to and managed by the original controller. Added devices cannot pair, unpair, reconnect to, accept physical input from, or forward input for a remote. Configuration/API/wire requests cannot delegate those permissions. Existing unrelated bonds on an adopted board are retained but disabled; adoption and migration do not clone, move, or erase bonds implicitly.

The one remote may select activities for different screens/zones through the original activity controls. This amendment does not remove zones, concurrent sessions, shared-resource arbitration, or browser control of multiple screens. A change of selected activity/screen stays on the same original controller. It cancels the affected held gesture, preserves exact-token cleanup, and never moves pairing ownership. Matter/HomeKit continue publishing one explicitly selected primary zone from that same controller. Their battery endpoint describes the sole remote, with unknown/unavailable state when appropriate.

No new remote/input gateway exists on a member, including while the original controller is offline. The protocol has no input-gateway, ingress-lease, remote-management or promotion message paths. Unknown/removed kinds reject; a valid leaf certificate grants only the current bounded actuator contract.

## Migration and restoration

New schema-1 migration binds the proven original singleton's stable ID. A readable older schema-2 document may omit `controller_octopus_id` only for compatibility. Before positive input/control is enabled, a bounded migration must bind it once from authenticated durable original-controller evidence. If that evidence is unavailable or conflicts with a previously moved coordinator, enter a passive diagnostic/recovery state. Never guess the original device from ordering or assign authority because a configuration file says so.

The sole physical remote bond belongs only to the controller, outside portable configuration. No remote-owner, primary-remote or button-mapping record exists in the current configuration model. Older mistaken fields, if encountered during explicit metadata migration, cannot activate/copy a foreign bond or create authority. Normal configuration edits, ordinary import/restoration, actuator replacement and member synchronization reject a different controller or a member-owned remote/input role. The explicit fresh-main recovery restore below may remap portable metadata to its newly proven authority; a backup is never itself evidence of authority.

Actuator replacement still uses fresh hardware identity/keys, explicit old-device isolation/revocation and confirmed attachment/equipment mapping. It preserves valid logical component/activity IDs without copying remote bonds, integration identities or credentials. In-place promotion or automatic substitution remains unsupported. If the main fails, the user can replace it and restore a portable configuration using the supported manual recovery below.

## Manual main replacement from a configuration backup

The user may save a portable configuration backup before a failure, replace the failed main Amity device, and restore that configuration. Use the existing **Advanced → Upload/Restore** workflow; do not add a recovery wizard, new UI destination, election or planned authority-transfer protocol.

1. Explicitly confirm that the old main is offline and physically isolated from control. An offline failure does not remotely erase its keys or prove that it can never restart; keep it isolated before using replacement authority.
2. Install the same firmware on fresh replacement hardware and complete Matter BLE setup. The replacement's own hardware identity, checked Wi-Fi/fabric state and durable role CAS establish its new main authority. The backup cannot establish or impersonate that authority.
3. Restore the portable backup through the replacement main's ordinary Advanced upload/restore. Preserve valid logical ComponentIds/ActivityIds, activity names/order, slots, aliases and other nonsecret choices. Rebase installation/owner references only to proven new identities. The implemented cross-main restore drops old executable bindings/resources/routes, remote assignment, PA evidence and old member domains; all restored activities initially remain disabled. After fresh native discovery, use the original Scan HDMI and Edit/Save controls to repair supported direct paths. Unsupported receiver/audio/switch paths remain explicitly unavailable until their ACT-01 implementation is complete. Preserve missing equipment and unmatched attachments with stable logical references; never guess hardware mappings, restore stale logical addresses or issue wake/routing/input during restore.
4. Re-pair the sole remote and establish Matter/HomeKit associations on the new hardware. Do not copy remote bonds, home-integration pairing databases, private keys, network/admin credentials or the old controller's identity from the backup.
5. On each old headless member, hold its setup/reset button for **at least ten seconds** to perform the existing durable factory-reset workflow. An unreset member cannot reopen candidate enrollment. This clears default-NVS Wi-Fi/fabrics/bonds and group operational credentials/configuration, while deliberately retaining its `amity_origin` stable hardware ID and bootstrap verifier/Add code. Then hold for **at least three but less than ten seconds** and release to open its bounded candidate enrollment window; re-add it through the replacement main's Amity tab using its retained Add authorization. Fresh TLS keys/leaf and new roster trust are required, even though the hardware ID can match the saved logical member. The new main must not trust old certificates, leases, prepared plans or execution grants. Validate current attachments/bindings before accepting fresh activity intent. A USB reclaim that preserves old fabrics is not documented as an equivalent recovery shortcut.

The result is supported **manual recovery**, not automatic failover or transparent handover. Normal reconnect of an existing installation still waits for its original main. If the old main returns, it retains no authority in the replacement installation and must remain isolated or be explicitly reset/reclaimed before reuse. Restoring logical configuration never resumes a previous activity or held gesture automatically.

## Loss, restart and updates

Loss of the original controller stops new plans and user control. Actuators retain isolation, finish already-started frames, release/expire exact held tokens, and become unavailable for new positive work. They do not offer an emergency UI, self-promote, elect a successor or replay activity after reconnection. Original-controller restart restores only suspended logical requests; fresh explicit Select/Resume creates new plans.

Update subordinate actuators first and the original controller last. A planned controller reboot is an explicit interruption, not permission for another device to take over. Existing handover/prepared-successor records or requests from the superseded profile must be rejected or held passive for explicit recovery; they cannot restore removed promotion authority. Credential renewal on the same original hardware must preserve the controller ID and use authenticated durable pin/key transitions.
