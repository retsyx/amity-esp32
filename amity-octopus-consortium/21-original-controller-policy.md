# Original controller, headless owners and original algorithms

This document records the user's authoritative role and execution requirements. [AGENTS.md](../AGENTS.md), [addressing](03-domain-model-and-addressing.md), [local execution](07-activity-planning-and-execution.md), [storage](11-configuration-storage.md) and [UI](20-user-interface.md) apply together.

## Original algorithms and functionality amendment — 21 October 2026

The current behavior baseline is `98e64a6` plus explicit user amendments. Preserve original activity/AVR/audio/switch behavior, discovery and physical-address selection, received-frame handling, remote input/macros/swipes, CEC transmission/attempts, independent key lifecycle and original UI workflows. Distribution moves original intents to an owner; it has zero effect on CEC behavior. Older design proposals and tests cannot authorize different normal-operation algorithms or timing.

The **29 October 2026 scan/cache amendment** explicitly limits HDMI enumeration to boot, an explicit UI request or actual communication with an uncached recipient. Lookup scans have a 120-second cooldown independently per owner/adapter/side; boot/UI scans bypass eligibility and refresh side timestamps. Activity edits do not disconnect Amities, clear HDMI caches or prune unreferenced observations. Reconnects, periodic timers and cooldown expiry do not independently scan. These explicit rules supersede contrary baseline scan triggers while preserving other CEC behavior; see [discovery](05-discovery-and-topology.md).

The **29 October 2026 execution amendment** requires one original Start/Standby sequence at a time per Amity, with just-in-time device resolution and each original command completing before the next step. Other Amities may advance in parallel. Every device caller uses the single cache-first resolver, including received-frame handlers; no cache-only or availability-preflight path is added. During an activity transition, ignore key presses before pressed-state registration; an unregistered release is a no-op, without ignored-press bookkeeping or replay. Preserve the existing physical-input gate and normal independent multikey behavior after it clears. See [activity execution](07-activity-planning-and-execution.md).

Each held key continues after its own successful completion while down. Other input/commands submit immediately. A failed key press ends it and later matching up is a no-op. Release is implicit at the end of the recipient's entire press stream, aggregated per physical wire/initiator/destination, with exact cleanup state retained separately. CEC has the only outgoing FIFO: eight total queued-plus-active messages per wire, releases included. Full-FIFO release stays dropped; log every full-FIFO TX drop. Bounded causal IPC is allowed; hidden outgoing/retry queues are not. [CEC contract](06-cec-roles-and-message-policy.md).

Keep startup/accepted-selection wait-for-release, its one-second fallback and swallowed holds; rejected selection and long-Power repair do not arm it. Keep Siri-only fixed Power/selector macros and unchanged swipe recognition, timing, generated events and cancellation. No per-button renewal or periodic transmitted press stream is added.

## Fixed original controller

One firmware serves both roles. An unclaimed board or proven original main with retained authority automatically opens bounded Matter setup at boot when its current fabric count is zero, including after factory reset and still-unclaimed reboots, without a button dependency. This is a permanent user requirement. A fresh unclaimed board has no saved Wi-Fi/UI; Matter BLE enrollment establishes the original controller and authenticated Amity BLE enrollment establishes a headless added device. Commit the durable role before original-only services or adoption acknowledgment. A committed Matter fabric, disarmed fail-safe and checked persistent connected Wi-Fi, or proven retained original authority, establish original role; a portable document, uncommitted fabric, discovery order or merely receiving Wi-Fi does not.

The first-setup device stays the original controller, sole remote owner, browser/admin host, Matter/HomeKit integration gateway and membership/configuration authority. Its stable ID is explicit, never inferred from hostname, array order, uptime or peer epoch. Reboot, last-fabric removal, rename/reorder, ordinary restore or another screen cannot change it. A proven original main with no remaining fabric reopens Matter setup automatically at boot while keeping its main role/UI/authority and explicit Matter-tab controls. Headless/prepared/member/retired/recovery roles do not open it automatically, even without fabrics; a current fabric prevents automatic opening. Neither commissioning history nor saved activities/configuration add a gate. Ambiguous identity/authority remains passive for recovery rather than guessed.

Added devices host no UI, login, status/recovery page, home integration or physical remote input path. They cannot accept delegated remote ownership, become input gateways, promote/elect themselves or offer automatic failover. Their authenticated management and owner-local execution wait for the original controller. Explicit physical/USB bootstrap/recovery remains separate from hosted UI.

## Settings, removal and manual recovery

Keep stable per-device adapter settings within the advertised one/four-adapter profile. Show one table with Adapter, Default, Detected Address and Selected Address columns. Configured-slot, boot, settings-revision, authority and deadline checks protect atomic live saves; they do not approve activity routes. Explicit default changes apply without reboot: select the adapter's stored latest scanned address when present, otherwise its new default. Ordinary scans update that observation without changing selection; the next default edit uses the latest result. Do not retain a redundant startup-source flag. Preserve member connections and discovery caches. There is no separate adapter-presence input; actual CEC responses and ACKs determine communication results.

Explicit Remove first lists and confirms every activity referencing the selected device. It deletes that device's saved owner/equipment/settings/name and the affected activities, revokes membership, drains/fences current work, commits the responding target's established reset journal and schedules only that target's restart after response attempt. Configuration/presentation and membership revisions, target boot and the exact activity set fence the user's review. Completion includes applied configuration and ordinary metadata cleanup; normal deleted-activity slot reservations retain no owner reference or alias. Replace remains a separate operation that remaps and preserves activity definitions while revoking and removing the isolated old device; it does not require destructive Remove first. Offline/unconfirmed removal requires the existing at-least-ten-second physical reset instructions. Generic loss, retirement or setup cancellation does not reset anything. Origin identity and factory Matter/admin credentials remain retained; operational trust/network/roles are reset-owned.

If the main fails, isolate it, Matter-enroll replacement hardware as a new main and use existing Advanced upload/restore. Preserve portable IDs, original fields/selectors/order/slots and explicitly map replacement owners; drop obsolete schema-2 executable approvals, old addresses and activity-resume state. Do not disable restored activities pending graph repair. Pair the sole remote and home integrations again; never clone old private keys, pairing stores, network/admin credentials or controller authority.

Factory-reset each old headless member with the existing ≥10-second hold, then use its three-to-below-ten-second candidate window and Amity devices → Add to re-enroll with fresh trust. Only the stricter matched build asks for the existing printed Matter code. A returning old main stays isolated until explicitly reset/reclaimed. There is no live transfer, member promotion or automatic failover. [Recovery](13-faults-removal-and-recovery.md).
